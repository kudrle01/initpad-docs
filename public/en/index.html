InitPad Help

The public edition connected to GitHub. Describes version 0.2.17; anything that applies only from a later version says so.

1. Getting started

InitPad creates a repository with an application skeleton and a ready-made pipeline for you, and after every push it builds, tests and deploys the application to your server. You write the code; you do not have to set up Docker or CI.

You will need:

  • a GitHub account,
  • a Linux server with Docker for the application to run on. It only needs outbound internet access, so it can sit behind a router or a VPN.

The whole path has five steps:

  1. Sign in with your GitHub account.
  2. Install the GitHub App so InitPad may work with your repositories.
  3. Connect a server with a single command.
  4. Create a project from a template, or import an existing repository.
  5. Push a change. InitPad deploys it to the dev environment and you then promote it further.
Help inside the app
The Help link in the left menu opens this page in the language you use in InitPad. The Learn more links on individual screens go straight to the matching chapter.

2. Signing in

On the start page choose Continue with GitHub. Your InitPad account is created on the first sign-in; there is no password to set.

A sign-in lasts seven days. After a platform update you may have to sign in again.

Under Account settings, the Signed-in browsers section lists every device where you are signed in. Sign out any browser you do not recognise, or choose Sign out all others.

3. Connecting GitHub

InitPad does not work with repositories in your name but through a GitHub App. It sees only the accounts and organizations you install it into, and only the repositories you allow.

  1. Open Account settings and in the GitHub account section choose Install GitHub App. A GitHub window opens, so allow pop-ups.
  2. Pick your account or organization and decide whether the App sees all repositories or only selected ones.
  3. When you come back, the installation appears in the list under your account. Add another account or organization with Add installation.
Organizations
An installation into an organization must be approved by its owner. If that is not you, GitHub sends the owner a request and InitPad shows that it is waiting for approval.

Membership in an organization is not enough. You will see the organization's repositories in InitPad only after the App is installed into it.

4. Connecting a server

Applications do not run at InitPad but on your server. A small program, InitPad Agent, runs there and fetches its work on its own. InitPad never connects to your server, so you do not have to open any management port or hand over an SSH key.

What the server needs

  • Linux and a running Docker,
  • outbound HTTPS to the InitPad address,
  • administrator rights to run the installer once.

Steps

  1. Open Servers and choose Add server.
  2. Keep InitPad Agent for Docker (recommended) as the connection method and fill in a name.
  3. In Can run, tick the runtimes the server can handle. A template can be deployed only to a server that supports its runtime.
  4. Choose the Application exposure (see the table below) and fill in the server's public URL.
  5. InitPad shows the Install and enroll on the Docker server command. Copy it and run it on the server. The installer asks for the enrollment token shown in the same window.
  6. After a moment the server appears as connected in the list.
ExposureWhen to choose itApplication address
Direct portsTrying things out, a lab, a server on an internal networkThe server address and a port. The port may change on a new deployment.
Managed gatewayProductionA stable address for each project and environment. Requires your own domain pointed at the server.
A server behind a VPN or at home
That works. The Agent only makes outbound connections and checks by itself that the application responds after a deployment. The application can then be opened only by someone who can reach the server, typically someone on the same network or VPN.

5. New project

  1. Choose New project and enter a name: lowercase letters, digits and hyphens.
  2. In GitHub repository owner, pick the account or organization where the repository should be created.
  3. Pick a Template and a Pipeline, i.e. which environments the project has: dev, test and prod; dev and prod only; or prod only.
  4. Under Deployment targets, assign a server to each environment. One server can host several environments.
  5. Choose Create project.

InitPad creates a private repository with the application skeleton, a Dockerfile and a GitHub Actions workflow, and sets the secrets it needs. The first pipeline run starts right away; when it finishes, the application is deployed to the dev environment.

6. Importing an existing repository

On the New project page choose Import existing repository. InitPad does not change your code during the import. The repository must however meet three conditions, which InitPad checks before importing:

ConditionDetails
DockerfileIn the root of the default branch. Purely static templates do not need one.
InitPad workflowExactly in the file .github/workflows/ci.yml. Download the starter version on the import screen and commit it yourself.
Repository nameLowercase letters, digits and hyphens, at most 41 characters. It becomes the project name.

A project that already has its own pipeline

  • Your workflows in other files keep running unchanged.
  • InitPad reads the status only from ci.yml. If your pipeline already has that name, rename it or add the InitPad steps to it.
  • Only the InitPad workflow triggers a deployment. If your tests in another file fail, InitPad does not see it and deploys anyway. Tests that should stop a deployment belong in ci.yml.
  • The application must listen on the port of the chosen template and answer on its health-check path, otherwise the deployment ends with a failed health check.

7. Deployments and environments

A push to the default branch starts the pipeline. It tests the application, builds an image and hands it to InitPad, which deploys it to the dev environment. The very same image is promoted to the next environments; nothing is rebuilt.

8. Variables and secrets

The project detail has a Configuration section with variables for each environment separately. InitPad passes them to the application on deployment. A change takes effect only after the environment is redeployed.

Secret values are stored encrypted and nobody can see them after saving, not even you. You can only replace a secret with a new value or delete it. Rolling back changes the application code; the variables stay as they are.

9. Team and roles

Projects, servers and GitHub App installations belong to a workspace. Besides your personal workspace you can create a team one from the workspace menu in the left sidebar with Add new workspace. In the public edition one account can own at most five team workspaces.

A personal workspace is yours alone. Add members to a team workspace in Workspace settings (the Workspace menu item), in the Workspace members section, with Add member. Enter a username or e-mail. The person must have signed in to InitPad at least once, otherwise their account does not exist.

A workspace member has one of five roles:

RoleWhat it adds to the previous one
viewerView projects and their status.
memberCreate and import projects, and deploy.
maintainerAdd servers and approve production deployments.
adminInstall the GitHub App for the workspace and manage members.
ownerChange the production approval rule.

A workspace can require production to be approved by someone other than the requester. The Audit log shows who did what.

10. Renaming and deleting

Renaming a repository or organization

From version 0.2.18 InitPad follows renames on GitHub by itself. The project picks up the new name shortly and the next push deploys as before. The container on the server keeps its original name so the running application does not move.

Version 0.2.17 and older
Do not rename a repository that has a project. The project would keep showing the old name and a new push would not deploy.
Transferring a repository
A transfer to another owner is not a rename. When the repository is no longer available to the GitHub App installation, InitPad treats it as deleted and cleans the project up.

Deleting a project

  1. For every environment deployed through the Agent, first choose Remove deployment and wait for the cleanup to finish.
  2. Choose Delete project.
  3. Tick Also delete the source repository and release its name only if you also want to delete the repository on GitHub. Without it, the repository stays and can be imported again later.

12. Public edition limits

  • Applications are deployed only to servers with the Agent. The public edition cannot deploy to shared web hosting over SFTP yet.
  • GitHub is the source of code. The public edition does not support other Git servers.
  • An application on a server behind a VPN is reachable only from that network. InitPad does not publish it to the outside.
  • The InitPad workflow must be in the file ci.yml.
  • One account can own at most five team workspaces.
