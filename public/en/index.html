InitPad Help

The public edition connected to GitHub and self-hosted installations. Describes version 0.2.35.

1. Getting started

InitPad creates a repository with an application skeleton and a ready-made pipeline for you, and after every push it builds, tests and deploys the application to your server. You write the code; you do not have to set up Docker or CI.

Two editions

InitPad comes in two editions. Most of this guide applies to both; differences are always stated in the text.

Public edition (GitHub)Self-hosted edition
Where it runsOperated by the InitPad author at https://staging.initpad.me (currently a trial service).On your own server. The administrator picks the address during installation, for example http://localhost:8080 or https://initpad.school.example.
Signing inWith a GitHub account.With a username and password; accounts are created by the instance administrator.
Repositories and CIGitHub and GitHub Actions, workflow .github/workflows/ci.yml.The built-in Gitea and its CI runner, workflow .gitea/workflows/ci.yml.
ServersYour own servers with InitPad Agent, or publicly reachable SFTP hosting.The same, plus platform servers the administrator makes available to a workspace.
Chapters for this edition onlySigning in, Connecting GitHub, Public edition limitsSelf-hosted InitPad

What you need

  • in the public edition a GitHub account, in the self-hosted edition an account from the instance administrator,
  • a Linux server with Docker for the application to run on (see server requirements). It only needs outbound access to the InitPad address, so it can sit behind a router or a VPN.

In the public edition the path has five steps:

  1. Sign in with your GitHub account.
  2. Install the GitHub App so InitPad may work with your repositories.
  3. Connect a server with a single command.
  4. Create a project from a template, or import an existing repository.
  5. Push a change. InitPad deploys it to the dev environment and you then promote it further.

In the self-hosted edition steps 1 and 2 do not apply: you sign in with a password and repositories are created in the built-in Gitea. See Self-hosted InitPad.

Help inside the app
The Help link in the left menu opens this page in the language you use in InitPad. The Learn more links on individual screens go straight to the matching chapter. The language switch at the top keeps the chapter you are reading.

2. Signing in

This chapter applies to the public edition. Signing in to a self-hosted edition is described in Password sign-in and account activation.

On the start page choose Continue with GitHub. Your InitPad account is created on the first sign-in; there is no password to set.

A sign-in lasts seven days. After a platform update you may have to sign in again. When a new InitPad version is released while a tab is open, the tab shows InitPad was updated; load the new version with Reload.

Under Account settings, the Signed-in browsers section lists every device where you are signed in. Sign out any browser you do not recognise, or choose Sign out all others.

3. Connecting GitHub

This chapter applies to the public edition. The self-hosted edition does not use GitHub.

InitPad does not work with repositories in your name but through a GitHub App. It sees only the accounts and organizations you install it into, and only the repositories you allow.

  1. Open Account settings and in the GitHub account section choose Install GitHub App. A GitHub window opens, so allow pop-ups.
  2. Pick your account or organization and decide whether the App sees all repositories or only selected ones.
  3. When you come back, the installation appears in the list under your account. Add another account or organization with Add installation.
Organizations
An installation into an organization must be approved by its owner. If that is not you, GitHub sends the owner a request and Settings shows Waiting for a GitHub organization owner to approve the App. The organization connects here once they do. Once the owner approves the App and you return to the InitPad window, the organization connects by itself.

Membership in an organization is not enough. You will see the organization's repositories in InitPad only after the App is installed into it.

4. Connecting a server

Applications do not run at InitPad but on your server. InitPad supports two kinds of servers:

Connection methodFor whatWho may add it
InitPad Agent for Docker (recommended)All templates. A small program, InitPad Agent, runs on the server and fetches its work on its own. InitPad never connects to the server, so you do not open a management port or hand over an SSH key.Workspace owner or admin
SFTP shared web hostingStatic sites and PHP (Nette, Laravel, Symfony) on ordinary web hosting. InitPad connects to the hosting itself over SFTP.Workspace owner, admin or maintainer

An Agent server may be added only by someone who may also connect the Agent, that is a workspace owner or admin. A workspace maintainer may add and verify an SFTP server and use every server the workspace already has. Other roles can only see servers.

What an Agent server needs

  • Linux (amd64 or arm64) with Docker Engine running as root, i.e. with the socket at /var/run/docker.sock. The Agent does not support rootless Docker. No desktop environment is needed.
  • Outbound HTTPS to the InitPad address. Only the managed gateway needs inbound ports (80 and 443).
  • Root rights to run the installer once.

Before enrolling, the installer checks the server size. Below the minimum it stops and lists what is missing; between the minimum and the recommendation it only warns.

MinimumRecommended
RAM1.5 GB4 GB
CPU12
Free space for Docker10 GiB20 GiB

The minimum is enough for the Agent and one environment, the recommended size for a project with dev, test and prod. By default each environment is limited to 512 MB of memory and 1 CPU, and while a new version is deployed the old and new versions briefly run side by side.

Steps for an Agent server

  1. Open Servers and choose Add server.
  2. Keep InitPad Agent for Docker (recommended) as the Connection method and fill in the Name.
  3. Choose the Application exposure (see the table below) and fill in the Application base URL, or the Gateway base URL for a managed gateway.
  4. In Can run, tick the runtimes the server should offer. A template can be deployed only to a server that supports its runtime. The Agent confirms Docker support by itself after enrollment.
  5. Choose Add server. The InitPad Agent dialog opens; later you open it with Manage Agent on the server. When you are at the server, choose Generate enrollment.
  6. 1. Install and enroll on the Docker server: copy the command and run it in an interactive terminal on the server. It verifies the installer checksum and the Agent image, checks the server size and starts the Agent. Download script only downloads the installer without running it.
  7. 2. Enrollment token: paste the token when the installer asks for it. It is entered through a hidden prompt, so it never enters shell history. The token is shown only once, disappears when you close the dialog, and is short-lived and single-use.
  8. After a moment the dialog shows Agent … is current and the server appears as connected in the list.
ExposureWhen to choose itApplication address
Direct ports (local / lab)Trying things out, a lab, a server on an internal networkThe server address and a port, for example http://192.168.1.50:32768. The port may change on a new deployment.
Managed gateway (production)Production, stable HTTPS addressesA stable address for each project and environment, for example https://shop-prod-1a2b3c4d.apps.example.com. Requires a domain, see Managed gateway.
A server behind a VPN or at home
That works. The Agent only makes outbound connections and checks by itself that the application responds after a deployment. The application can then be opened only by someone who can reach the server, typically someone on the same network or VPN.

Managed gateway

The gateway gives every environment a stable HTTPS address under your domain. The Agent installer sets it up on the server by itself: a private certificate authority (CA), a TLS edge on ports 80 and 443 and an inner gateway.

  1. Pick a domain for the applications, for example apps.example.com. It must be a DNS name, not an IP address.
  2. In DNS, point two records at the server: the domain itself, apps.example.com, and the wildcard *.apps.example.com. On an internal network create them on your own DNS server.
  3. Allow inbound ports 80 and 443 on the server and in the firewall. No other web server may occupy them. If ufw is active, the installer adds the rule it needs by itself.
  4. When adding the server, choose Managed gateway (production) and enter https://apps.example.com as the Gateway base URL.
  5. Run the install command from the Agent dialog. It contains --gateway-domain apps.example.com and at the end prints the SHA-256 fingerprint of the CA certificate.
  6. In the Agent dialog, in the Application gateway section, choose Test gateway. The test is read-only: it checks the wildcard DNS, trusted TLS on port 443 and the inner gateway without changing any route. The server can receive deployments once the test passes.
  7. Install the gateway certificate on the computers that open the applications.

Agent 0.16 and newer refresh the gateway themselves after an update. For an older Agent, or if that did not happen, run the command from the collapsible Refresh the gateway on the server section on the server; no enrollment token is needed. Changing the exposure or the gateway URL resets the test result and the gateway must be tested again.

Gateway certificate

The gateway signs the applications' HTTPS certificates with its own CA. Browsers trust them once you install that CA, which you do once per computer.

  1. In the Agent dialog, in the Gateway certificate section, choose Download certificate. This downloads initpad-gateway-ca.crt from http://apps.example.com/initpad-ca.crt.
  2. Compare the fingerprint. The dialog shows SHA-256 fingerprint. Compare it with the downloaded file before installing it:. Get the file's fingerprint with openssl x509 -in initpad-gateway-ca.crt -noout -fingerprint -sha256. Until the gateway test has run, the dialog has no fingerprint; compare with the one the installer printed instead.
  3. Install the certificate for your system:
    • Windows: open the file → Install Certificate → Local Machine → Trusted Root Certification Authorities. Chrome and Edge then trust it too.
    • macOS: double-click the file, add it to Keychain Access (System) and in its trust settings choose Always Trust.
    • Firefox (it has its own certificate store): Settings → Privacy & Security → View Certificates → Authorities → Import and tick trust for identifying websites.
  4. Check the installation: restart the browser and open the address of a deployed application. The browser must not report an untrusted certificate, and the certificate details show the InitPad CA as the issuer.

SFTP hosting

InitPad deploys static sites (React, Vue) and PHP applications (Nette, Laravel, Symfony) to shared web hosting. PHP also needs shell access through the same account. Other templates need an Agent server.

Publicly reachable hosting only
Unlike with the Agent, InitPad connects to SFTP hosting itself. In the public edition the host and the public URL must therefore resolve to public internet addresses; hosting behind a VPN, on a home network or at a private address cannot be added. A self-hosted instance can also connect to hosting on its internal network.
  1. In Servers choose Add server and as the Connection method choose SFTP shared web hosting.
  2. Fill in the Name and Port (usually 22) and in Can run tick Static and, if needed, PHP.
  3. Fill in the Host and Username, and in Auth choose Password, or SSH key and paste an OpenSSH private key.
  4. Choose Get fingerprint. InitPad retrieves the server's public key without sending the password. Compare the fingerprint with the value from the hosting administrator and confirm with Trust and save. InitPad requires exactly this key for every later connection.
  5. Fill in the Remote path (the site directory, for example /www/myapp) and the Public URL where the site is visible.
  6. Choose Add server, then Test connection on the server. Only a verified server can receive deployments.

Agent updates and the offline state

When a new Agent version is released, the Manage Agent dialog shows Agent … is available. Agent 0.13 and newer update remotely with Install update: only the Agent container is replaced, applications keep running, and if the new Agent cannot sign in, the previous one is restored. The Agent must be online for this. An older Agent gets a one-time manual command to run on the server; the server identity is kept and no new token is needed.

A server is offline when no heartbeat has arrived from the Agent for 90 seconds. The dialog then shows Agent is offline and the time of the last contact. Jobs wait safely in the queue and continue once the Agent is back; a deployment meanwhile shows Waiting for Agent. Check that the server is running, Docker is started and the server can reach the InitPad address. If the Agent container is not running, run the command from the Reconnect Agent section of the dialog on the server.

Disconnecting, retiring and deleting a server

A server has a Disconnect and delete section with three buttons:

ButtonWhat it does
Disconnect serverInitPad stops managing the server and revokes its access. Running applications stay online.
Retire serverFor a server you are shutting down. History and URLs stay visible; deployments on it can then be released.
Delete serverRemoves the server from InitPad. Nothing on the server itself is deleted.

A disconnected server can be deleted only when none of its environments still records a deployment. Otherwise InitPad shows Release the deployments on this server first: …; release them with Release deployment, see Deployments and environments.

Uninstalling the Agent from a server

In the Manage Agent dialog, expand Diagnostics and removal → Uninstall from the server and run the command on the server. It verifies the installer checksum, refuses a server enrolled for another target, lists what it removes and asks you to confirm. It removes the Agent container, its saved identity and the InitPad CA installed for it. The section is also available for a disconnected Agent. A managed gateway on the server stays.

The Also remove applications InitPad deployed on this server option deletes their containers and networks directly on the server. InitPad keeps showing them as deployed, so prefer removing environments in InitPad while the Agent is connected. After uninstalling, disconnect the Agent in InitPad or delete the server, so InitPad no longer waits for it.

5. New project

  1. Choose New project and enter the Project name: 2–41 lowercase letters, digits or hyphens, starting with a letter. The name is also used for the repository and the application address.
  2. In the public edition, pick the account or organization where the repository should be created in GitHub repository owner. In the self-hosted edition the repository is created in the built-in Gitea.
  3. Pick a Template and a Pipeline, i.e. which environments the project has: dev, test and prod; dev and prod only; or prod only.
  4. Under Deployment targets, assign a server to each environment. One server can host several environments. A server that cannot be used yet shows why, for example Agent not ready or gateway check failed.
  5. Choose Create project.

InitPad creates a private repository with the application skeleton, a Dockerfile and a CI workflow, and sets the secrets it needs. The project page then shows Preparing the project… and, once the first pipeline starts, Building the first version…; it refreshes by itself. When the pipeline finishes, the application is deployed to the dev environment.

When something goes wrong

SituationWhat to do

6. Importing an existing repository

On the New project page choose Import existing repository. InitPad does not change your code during the import. The repository must however meet three conditions, which InitPad checks before importing:

ConditionDetails
DockerfileIn the root of the default branch. Purely static templates do not need one.
InitPad workflowExactly in the file .github/workflows/ci.yml (public edition) or .gitea/workflows/ci.yml (self-hosted). Download the starter version on the import screen and commit it yourself.
Repository name2–41 lowercase letters, digits or hyphens, starting with a letter. It becomes the project name.

A project that already has its own pipeline

  • Your workflows in other files keep running unchanged.
  • InitPad reads the status only from ci.yml. If your pipeline already has that name, rename it or add the InitPad steps to it.
  • Only the InitPad workflow triggers a deployment. If your tests in another file fail, InitPad does not see it and deploys anyway. Tests that should stop a deployment belong in ci.yml.

7. Deployments and environments

A push to the default branch starts the pipeline. It tests the application, builds an image and hands it to InitPad, which deploys it to the dev environment. The very same image is promoted to the next environments; nothing is rebuilt.

8. Variables and secrets

The project detail has a Configuration section with variables for each environment separately. InitPad passes them to the application on deployment. A change takes effect only after the environment is redeployed.

RuleDetails
KeyUppercase letters, digits and underscore, not starting with a digit (^[A-Z_][A-Z0-9_]*$), for example DATABASE_URL.
Reserved keyInitPad sets PORT from the template; it cannot be saved.
ValueAt most 8192 characters.
Running operationWhile an environment is deploying or running another operation, its variables cannot be changed. Wait for it to finish.

Secret values are stored encrypted and nobody can see them after saving, not even you. You can only replace a secret with a new value or delete it. Rolling back changes the application code; the variables stay as they are.

9. Team, roles and quotas

Projects, servers and GitHub App installations belong to a workspace. Besides your personal workspace you can create a team one from the workspace menu in the left sidebar with Add new workspace. In the public edition one account can own at most five team workspaces; the self-hosted edition has no such limit by default.

A personal workspace is yours alone. Add members to a team workspace in Workspace settings (the Workspace menu item), in the Workspace members section, with Add member. Enter a username or e-mail. In the public edition the person must have signed in to InitPad at least once; in the self-hosted edition the instance administrator must create their account first.

A workspace member has one of five roles:

RoleWhat it adds to the previous one
ViewerView projects, servers and their status.
MemberCreate and import projects, deploy and change variables.
MaintainerAdd and verify SFTP servers, edit servers, change the project pipeline and approve production deployments.
AdminAdd Agent servers and connect the Agent, manage workspace access to servers, install the GitHub App for the workspace and manage members.
OwnerChange the production approval rule.

A workspace can require production to be approved by someone other than the requester. The Audit log shows who did what.

Workspace quotas

Every workspace has limits, shown in Workspace settings under Workspace capacity. A platform administrator can raise them.

LimitDefault
Projects50
Members100
Servers20
Concurrent operations (deployments and setups)10
Artifact storage20 GiB

On each server the workspace also has its own limits: by default at most 50 environments and, per environment, 1 CPU, 512 MB of memory and 256 processes. Change them on the server with Edit access.

10. Renaming and deleting

Renaming a repository or organization

In the public edition InitPad follows renames on GitHub by itself. The project picks up the new name shortly and the next push deploys as before. The container on the server keeps its original name so the running application does not move.

Transferring a repository
A transfer to another owner is not a rename. When the repository is no longer available to the GitHub App installation, InitPad treats it as deleted and cleans the project up.

Deleting a project

  1. For every environment deployed through a connected Agent, first choose Remove deployment and wait for the cleanup to finish. Release deployments on a disconnected or retired server with Release deployment, or let the dialog flag them.
  2. Choose Delete project.
  3. Tick Also delete the source repository and release its name only if you also want to delete the repository. Without it, the repository stays, its name stays taken, and it can be imported again later.

A project with a deployment on a disconnected or retired server can be deleted too. The dialog marks that deployment server disconnected · left on the server and requires you to tick Delete the InitPad record with protected cleanup still pending. The containers may keep running there and must be removed on the server manually.

12. Public edition limits

  • SFTP hosting must be reachable from the internet. Connect a server behind a VPN or on an internal network through the Agent, if it runs Docker.
  • GitHub is the source of code. The public edition does not support other Git servers.
  • An application on a server behind a VPN is reachable only from that network. InitPad does not publish it to the outside.
  • The InitPad workflow must be in the file .github/workflows/ci.yml.
  • One account can own at most five team workspaces.

The self-hosted edition has different rules, see What is different in the self-hosted edition.

13. Self-hosted InitPad

A self-hosted InitPad runs entirely on your server: web, API, database, Gitea with a CI runner and artifact storage. This chapter is for users and administrators of such an instance. Detailed operating instructions are in the repository in deploy/README.md and deploy/OPERATIONS.md (in Czech).

Installation

The InitPad server needs Linux with Docker Engine and the Compose plugin, at least 2 CPUs, 6 GiB of RAM and 20 GiB of space for Docker (4 vCPUs, 8 GiB and 40 GiB recommended). On Ubuntu 24.04 and newer, run sudo ./prepare-rootless-runner.sh first; the installer tells you if it is needed.

git clone https://github.com/kudrle01/initpad.git
cd initpad/deploy
./install.sh

On the first run the installer asks how users will open InitPad:

OptionWhenAddress and HTTPS
Only this computerTrying it out on your own computerhttp://localhost:8080, no HTTPS
Internal network with DNSA school or company with names on its own DNS serverFor example https://initpad.school.example, InitPad's own certificate authority
Public domainA server reachable from the internet on ports 80 and 443For example https://initpad.example.org, a Let's Encrypt certificate
Local network by IP addressFrom the release following 0.2.35. A lab or virtual machine without DNS; InitPad is opened by the server's IP address.An address like http://192.168.1.50:8080

The options with a domain need two DNS records pointing at the server: the platform name and the Git name (for example git.school.example). At the end the installer prints the platform address, the setup token and, for an internal network, the certificate fingerprint. You can run the script again at any time and it only fixes what is missing; change the domain or mode with ./install.sh --reconfigure.

The first administrator

  1. Open the platform address the installer printed.
  2. Choose Create account and fill in a username, e-mail, password (at least 12 characters) and the Setup token from the end of the installer output.
  3. The first account becomes the platform administrator. It creates the other accounts, see below.

The message The setup token is not valid. Use the token printed at the end of install.sh. means the token is wrong. It is stored in deploy/.env as INITPAD_BOOTSTRAP_TOKEN.

Password sign-in and account activation

By default users do not register themselves; the administrator creates their accounts:

  1. The administrator opens Platform in the left menu and in the Users section chooses Add user.
  2. If the instance has e-mail configured, the user receives an activation link. Otherwise the link is shown once and the administrator passes it on securely. New activation link creates a new one and invalidates the old one.
  3. The user opens the link, chooses a password (at least 12 characters) on the Activate your account page and confirms with Activate and sign in.
  4. From then on they sign in on the start page with their username or e-mail and password. A sign-in lasts seven days.

The administrator can reset a password (the user gets a temporary password they must change at the next sign-in) or deactivate an account; a deactivated account cannot sign in to InitPad or Gitea.

Gitea and Git

Project repositories live in the built-in Gitea at the Git address the installer printed (http://gitea.localhost:3001 for a local installation). Sign in to Gitea with your InitPad account through single sign-on (SSO): on the Gitea sign-in page choose sign-in with initpad-sso. You do not create a separate Gitea password.

To work from the command line, open Account settings → Connect Git, choose Show setup command and run the command once in a terminal. You can then clone, pull and push without a password prompt. The command stores your personal Gitea token in ~/.gitconfig, so keep it private.

Platform certificate

An installation for an internal network issues HTTPS certificates from its own certificate authority. For the browser to trust InitPad and Gitea without a warning, install its certificate once on every computer:

  • in InitPad under Account settings → Platform certificate (the file initpad-root-ca.crt, its SHA-256 fingerprint and instructions for Windows, macOS and Firefox, the same as for the gateway certificate),
  • on a computer that does not trust InitPad yet, over HTTP from http://<platform name>/initpad-ca.crt; compare the fingerprint with the installer output,
  • in a Windows domain the administrator distributes it with a group policy into Trusted Root Certification Authorities.

Agent servers receive the platform certificate automatically: the command from the Agent dialog downloads it, checks the fingerprint and trusts it for the InitPad registry only. The platform certificate and the managed gateway certificate are two different files.

Workspace access to servers

Besides the workspace's own servers (added the same way as in the public edition), an instance can offer platform servers, for example the built-in Docker on the InitPad host (Docker · self-hosted direct). A workspace may deploy to them once a workspace owner or admin enables access:

  1. In Servers, on a server marked Not enabled for this workspace, choose Enable for ….
  2. Set the Allowed runtimes, the Environment quota, the CPU, memory and process limits per environment and, optionally, automatic cleanup of dev and test environments.
  3. Access can later be changed with Edit access, Pause access or Remove access. Running applications are not stopped.

The built-in Docker is meant for trying things out. On a local installation it publishes application ports on this computer only. For applications reachable from other computers use an Agent server, ideally with a managed gateway.

The Platform page and updates

Only platform administrators see Platform in the left menu. It holds user management, workspace capacity and the Platform updates section. The installed version is also shown at the bottom of the left menu.

  1. In Platform updates choose Refresh to load the list of signed releases.
  2. For a newer version choose Install update and confirm.
  3. InitPad backs up the database, replaces the API, web and Supervisor images and checks that the new version runs. The web UI and API restart briefly; project applications are not restarted.
  4. If the new version fails its checks, the previous one is restored automatically and the page shows The update to InitPad … did not complete. The previous version is running.

Agent servers are updated separately, see Agent updates.

Backup and restore

The administrator makes a backup on the server, in the deploy folder, with ./backup.sh /secure/path/initpad-backup. The backup contains the database, Gitea repositories, artifacts, configuration and credentials, so encrypt it and keep a copy off the server. Restore with ./restore.sh <backup directory>; try it on a disposable installation first. The exact procedure, scheduling and restore drills are in deploy/OPERATIONS.md, sections Zálohy (backups) and Obnova (restore).

What is different in the self-hosted edition

  • The Signing in and Connecting GitHub chapters do not apply. You sign in with a password; there is no GitHub App and no GitHub repository owner field.
  • Repositories live in Gitea, the workflow is in .gitea/workflows/ci.yml and pipeline logs are in Gitea. There is no button to re-run GitHub jobs.
  • Following repository renames and transfers, as described in Renaming and deleting, applies to GitHub only.
  • The limit of five team workspaces does not apply by default. Workspace quotas apply the same way.
  • SFTP hosting may also be on the internal network.
  • A new workspace member must first be created by the platform administrator.
  • In version 0.2.35 the Help and Learn more links appear only when the administrator sets INITPAD_DOCS_URL in deploy/.env. From the release following 0.2.35 they point to https://docs.initpad.me by default.
